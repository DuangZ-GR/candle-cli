# v0.4.0 Interactive Permission Gate Design

**Date:** 2026-05-09

## Goal

Add a real interactive permission gate to `candle-cli` so agent tool calls can be controlled by the user at runtime. The purpose of v0.4.0 is to move the project from a technically working coding-agent loop into a safer, user-steerable terminal assistant.

The system should allow read-only tool calls automatically when policy permits them, and require explicit terminal confirmation for write/command tools when running in prompt-confirmation mode.

## Confirmed Scope

### In scope

- Wire `PermissionMode` and `PermissionPolicy` into actual tool execution.
- Add a real interactive confirmation path for dangerous tool calls.
- Support these permission modes in runtime behavior:
  - `read-only`
  - `workspace-write`
  - `prompt`
  - `danger-full-access`
- Introduce an environment-based configuration path for permission mode.
- Treat user denial as a tool result fed back to the model.
- Add tests for allow, deny, and mode-specific behavior.
- Document how permission mode works in README.

### Out of scope

- GUI confirmation dialogs.
- Rich diff previews before approval.
- Per-tool allowlists or policy files.
- Persistent trust decisions.
- OS-level sandboxing.
- Approval batching across multiple tool calls.

## Recommended Approach

The recommended design is to keep the current multi-step tool loop intact and insert permission checks immediately before tool execution. The loop continues to own orchestration; `PermissionPolicy` becomes the decision point for whether a tool is:

1. allowed immediately,
2. denied immediately, or
3. requires interactive confirmation.

When confirmation is required, the CLI prompts the user in the terminal and waits for a yes/no decision. The result is then converted into a normal tool-result message so the model can adapt.

This approach avoids changing the model protocol and keeps the permission gate local to Rust, where the tool execution already happens.

## Permission Configuration

The first version should use an environment variable:

```text
CANDLE_CLI_PERMISSION
```

Accepted values:

- `read-only`
- `workspace-write`
- `prompt`
- `danger-full-access`

If unset, the recommended default remains `workspace-write` so existing behavior is preserved.

A helper in the CLI layer should parse the env var into `PermissionMode` and fall back safely on unknown values.

## Permission Semantics

### `read-only`

Allowed automatically:

- `pwd`
- `read`
- `glob`
- `grep`

Denied automatically:

- `edit`
- `write`
- `shell`

### `workspace-write`

Allowed automatically:

- all current tools

This preserves the current non-interactive coding-agent behavior.

### `prompt`

Allowed automatically:

- `pwd`
- `read`
- `glob`
- `grep`

Requires confirmation:

- `edit`
- `write`
- `shell`

### `danger-full-access`

Allowed automatically:

- all current tools

This mode behaves like an unrestricted version of `workspace-write` and mainly exists to keep naming aligned with future more dangerous tools.

## Confirmation UX

When a tool requires confirmation, the terminal should show a concise prompt such as:

```text
Allow tool call?
- tool: shell
- input: {"command":"cargo test"}
[y] allow
[n] deny
```

Input handling should be simple:

- `y` or `yes` → allow
- `n` or `no` → deny
- EOF or empty input → deny
- any other input → re-prompt once, then deny if still invalid

The goal is reliability, not a fancy UI.

## Integration Point

The permission gate should be applied in the agent loop after parsing a valid `ToolCallIntent` and before calling `ToolRegistry::execute`.

Flow:

```text
model emits tool call
→ Rust parses tool call
→ Rust evaluates permission policy
→ allowed: execute tool
→ denied: create denial tool result
→ prompt: ask user, then execute or deny
→ append ToolResult to session
→ continue loop
```

This keeps permission handling orthogonal to model behavior.

## Denial and Error Handling

If a tool is denied due to policy or explicit user refusal, append a normal `ToolResult` with `is_error: true`, for example:

```text
tool execution denied by user
```

or

```text
tool not allowed in read-only mode
```

This is important because the model should see the denial and choose another action or explain the limitation instead of losing loop continuity.

## Runtime API Shape

The cleanest structure is to introduce a small execution context owned by the CLI layer:

```rust
struct ExecutionContext {
    tools: ToolRegistry,
    permission_mode: PermissionMode,
}
```

Or, if less intrusive, pass a `PermissionPolicy` alongside `ToolRegistry` into `run_single_turn`.

The recommended design is:

```rust
run_single_turn(session, runtime, tools, policy)
```

This keeps `ToolRegistry` focused on executing tools and `PermissionPolicy` focused on whether execution is allowed.

## Interactive Confirmation Implementation

The existing `permissions/prompt.rs` is currently a stub. v0.4.0 should turn it into a real terminal confirmation helper.

Recommended behavior:

```rust
pub fn confirm_dangerous_action(tool_name: &str, input_json: &str) -> bool
```

It prints the prompt, reads a line from stdin, and returns `true` only for explicit allow input.

The helper should stay synchronous and terminal-based. That is enough for the current REPL/prompt architecture.

## Testing Strategy

### Permission policy tests

Expand `tests/permissions/test_policy.rs` to verify:

- read-only allows read tools and rejects write tools.
- prompt mode marks `shell/edit/write` as requiring confirmation.
- workspace-write allows current tools directly.
- danger-full-access allows current tools directly.

### Agent loop tests

Add scripted-runtime tests that verify:

- in read-only mode, `shell` becomes an error tool result and the model can continue.
- in prompt mode, a denied `shell` tool call becomes `tool execution denied by user` and the loop continues to a final answer.
- in prompt mode, an allowed `edit` or `shell` tool call executes successfully.

### Confirmation tests

If the confirmation helper is factored to accept an input source, test it directly with simulated stdin-like data. If that is too invasive, cover it through integration tests.

### CLI integration tests

Add integration tests that set `CANDLE_CLI_PERMISSION` and verify prompt-mode behavior is reachable from `prompt`/REPL entry points.

## Documentation

README should explain:

- the `CANDLE_CLI_PERMISSION` env var,
- what each mode means,
- which tools are auto-allowed vs confirmation-gated,
- what a terminal approval prompt looks like.

Include examples such as:

```bash
CANDLE_CLI_PERMISSION=read-only cargo run -- prompt "读取 README.md 并总结"
CANDLE_CLI_PERMISSION=prompt cargo run -- prompt "运行 cargo test 并总结失败原因"
```

## Acceptance Criteria

v0.4.0 is complete when:

- permission mode is configurable at runtime,
- read-only mode blocks write/command tools,
- prompt mode interactively asks for confirmation on `edit/write/shell`,
- denial is returned to the model as a tool result,
- agent loop continues after denial or policy rejection,
- tests cover allow/deny behavior,
- README documents the permission modes and prompt UX,
- full verification passes.

## Deferred Follow-up Work

After v0.4.0, likely next steps are:

- diff previews for edit approval,
- per-tool persistent approvals,
- policy files,
- better shell command summaries,
- native OpenAI tool schema,
- streaming and richer UI.
